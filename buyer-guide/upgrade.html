Upgrade Guide

How to apply a new version of payload-portfolio without losing your content or personalisation.

🗄️
Content is untouched
All your posts, work, and settings live in MongoDB — the upgrade never touches your database
🔐
One file to protect
src/content/stack.ts is the only source file you edited — back it up before upgrading
⚡
~5 min process
Pull changes, install deps, restore your stack file, redeploy
💡
Read the CHANGELOG first. Every release lists what changed, what's new, and any breaking changes that require manual steps. Open CHANGELOG.md in the root of the project before starting.

Your Data is Safe

Upgrading replaces source code files — it never touches your database or environment variables. Here's where each type of data lives:

Data Where it lives Affected by upgrade?
Name, role, socials, philosophy MongoDB No — stored in your database, never in source files
Blog posts, work entries MongoDB No — all CMS content lives in the database
Uploaded images & PDFs Cloudflare R2 No — stored in your R2 bucket, not the repo
API keys & secrets .env.local No — .env.local is git-ignored and never overwritten
Your tech stack list src/content/stack.ts Yes — back this up before upgrading
Custom code changes source files Yes — any custom edits you made to components will need re-applying if those files changed in the update

Files to Protect

Before copying any new files into your project, save copies of these:

src/content/stack.ts always back up

The only source file you edited. Copy it somewhere safe before upgrading, then restore it after. Its format rarely changes between versions — but check the CHANGELOG to be sure.

.env.local always back up

Your environment variables. This file is git-ignored and is never included in downloads, so it can't be overwritten — but keep a copy offsite just in case.

public/ check for custom assets

If you replaced the default favicon, avatar image, or added your own icons here, back those files up. Updates may ship new files in public/ but won't delete existing ones (via git merge or careful ZIP copy).

src/app/globals.css check if you customised colours

If you changed the colour palette or design tokens, note your changes before upgrading. This file may be updated in new releases.

All other source files safe to overwrite

Components, pages, lib utilities, collections, globals, actions — these are all framework code maintained by updates. Unless you made custom edits to them, you can overwrite them freely.

⛔
Never overwrite .env.local with .env.example from the new release. .env.example only shows the variable names — it does not contain your values. Check if any new variables were added to .env.example and add only those to your existing .env.local.

Method A — Git recommended

If you pushed the project to your own GitHub repository, this is the cleanest upgrade path. Git handles the diff and won't touch files it didn't change.

1
Back up your stack file
cp src/content/stack.ts stack.backup.ts
2
Add the upstream remote (first time only)
git remote add upstream https://github.com/SELLER_REPO/payload-portfolio.git

Replace the URL with the repository URL provided in your CodeCanyon download page. You only need to do this step once.

3
Fetch the new release
git fetch upstream
git log upstream/main --oneline -10

Review the commits to understand what changed before merging.

4
Merge the update into your branch
git merge upstream/main --no-commit

--no-commit stages the changes but doesn't create the commit yet, giving you a chance to review the diff before finalising.

5
Resolve any conflicts

Most conflicts will be in src/content/stack.ts if you edited it. Accept your version of that file:

git checkout --ours src/content/stack.ts
git add src/content/stack.ts

For any other conflicts, compare the diff carefully and decide whether to keep your changes or accept the update.

6
Commit the merge
git commit -m "chore: upgrade to vX.Y.Z"
7
Check for new environment variables

Compare the new .env.example with your .env.local. If new variables were added, copy them to your .env.local and fill in the values.

diff .env.example .env.local

Method B — ZIP Download

If you're not using git, follow these steps to apply the update manually.

1
Back up your personalised files

Copy these somewhere outside the project folder before doing anything else:

  • src/content/stack.ts — your tech stack
  • .env.local — your API keys and secrets
  • Any custom assets you added to public/
  • Any custom code edits you made (note which files)
2
Download and unzip the new release

Extract the new ZIP to a temporary folder — not inside your existing project.

unzip payload-portfolio-vX.Y.Z.zip -d /tmp/payload-new
3
Read the CHANGELOG

Open /tmp/payload-new/CHANGELOG.md and read the entries between your current version and the new one. Look for any Breaking Changes or migration notes before copying files.

4
Copy the source directories

Replace the following directories in your project with the ones from the new release:

cp -r /tmp/payload-new/src/app        ./src/app
cp -r /tmp/payload-new/src/components ./src/components
cp -r /tmp/payload-new/src/lib        ./src/lib
cp -r /tmp/payload-new/src/collections ./src/collections
cp -r /tmp/payload-new/src/globals    ./src/globals
cp -r /tmp/payload-new/src/actions   ./src/actions
cp -r /tmp/payload-new/src/emails    ./src/emails
cp -r /tmp/payload-new/src/features  ./src/features
cp -r /tmp/payload-new/src/hooks     ./src/hooks
cp -r /tmp/payload-new/src/payload.config.ts ./src/payload.config.ts
⚠️ Do not copy src/content/stack.ts — this is your personalised file. Leave it as-is.
5
Copy the root config files

Replace these root-level files (they don't contain personal data):

cp /tmp/payload-new/next.config.ts   ./next.config.ts
cp /tmp/payload-new/tsconfig.json    ./tsconfig.json
cp /tmp/payload-new/vitest.config.ts ./vitest.config.ts
cp /tmp/payload-new/components.json  ./components.json
6
Check for new env variables

Compare the new example file with your live config and add any missing variables:

diff /tmp/payload-new/.env.example .env.local

Lines prefixed with < are in the new example but not your file — add those variables to your .env.local.

7
Copy updated package.json

Replace package.json with the new version so updated dependencies are pulled in:

cp /tmp/payload-new/package.json ./package.json

Install & Verify

Run these steps after applying either upgrade method.

1
Install updated dependencies
pnpm install

New releases may add, remove, or upgrade npm packages. Always run this after upgrading.

2
Start the dev server and check for errors
pnpm dev

Open http://localhost:3000 and click through the main pages. Open http://localhost:3000/admin and verify the admin panel loads correctly. Watch the terminal for any build errors.

3
Run the test suite
pnpm test

All tests should pass. A failing test after an upgrade usually means a breaking change in the CHANGELOG that requires a manual migration step.

4
Verify your stack file is intact

Open src/content/stack.ts and confirm your technologies are still there. Then visit http://localhost:3000/stack to check it renders correctly.

Breaking Change Checklist

When the CHANGELOG lists a breaking change, look it up here for the migration steps.

New environment variable required env change

Add the new variable to your .env.local and to your Vercel / hosting environment variables. The app will error on startup if a required variable is missing.

grep 'NEW_VAR' .env.example    # confirm the variable name
echo 'NEW_VAR=your_value' >> .env.local
Payload CMS collection schema changed cms change

Schema changes (new fields, renamed fields) are applied automatically when Payload starts — it reads the updated collection definitions and migrates the database. No manual SQL or migration scripts needed. Old data in removed fields is preserved in the database even if the field is no longer shown in the admin.

src/content/stack.ts type changed type change

Occasionally the shape of the stack data structure changes (e.g. a new field added to each item). The CHANGELOG will describe the change. Open your backup and the new stack.ts side-by-side and update your entries to match the new type. TypeScript will show a compile error pointing at the exact mismatch.

Major Next.js or Payload CMS version bump major version

Major framework upgrades (e.g. Next.js 16 → 17 or Payload 3 → 4) are treated as major releases of payload-portfolio. These will always have a dedicated migration guide in the CHANGELOG with step-by-step instructions. Do not skip this guide — major versions frequently have breaking changes in the framework API itself.

Redeploy

Once local verification passes, push and redeploy.

Vercel

1
Push to GitHub
git push origin main

If you're connected to Vercel via GitHub, pushing triggers an automatic redeploy. No manual action needed.

2
Add any new env vars in Vercel

If the CHANGELOG listed new required variables, add them to your Vercel project under Settings → Environment Variables before the new deployment goes live. The deployment will fail at runtime if a required variable is missing in production.

Self-Hosted (PM2)

git pull                 # pull the latest code (git method only)
pnpm install             # install any new deps
pnpm build               # build the new version
pm2 reload flcn-website  # zero-downtime reload

If you're using the ZIP method on a VPS, copy files and run pnpm install && pnpm build before reloading PM2.

FAQ

Will upgrading delete my posts or work entries?

No. All CMS content (posts, work, projects, timeline, site settings) lives in your MongoDB database. The upgrade only changes source code files. Your database is never touched.

I customised some components — will my changes be overwritten?

If you edited files outside of src/content/stack.ts, those changes will be overwritten by a fresh file copy. Use the git method — it will show you a conflict diff for each file you changed, and you can selectively keep your edits.

The admin panel shows an error after upgrading

Most likely cause: a new required environment variable was added and you haven't set it yet. Check the CHANGELOG for the new version, look for "new env var" entries, and add the value to .env.local. Also try clearing the .next/ build cache: rm -rf .next && pnpm dev.

Tests are failing after upgrading

Run pnpm test and read the failing test output. A test failure after an upgrade usually points to a breaking change that requires a migration step — find it in the CHANGELOG and follow the instructions.

The stack page is showing default entries, not mine

You accidentally overwrote src/content/stack.ts. Restore it from your backup. If you didn't make a backup, check your git history: git show HEAD~1:src/content/stack.ts > src/content/stack.ts.

How do I check which version I'm currently on?

Open package.json and read the "version" field. You can also check CHANGELOG.md — the top entry is the currently installed version.
